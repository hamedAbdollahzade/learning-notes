# Full Walkthrough: Workflow for AI Coding

- **سخنران:** Matt Pocock
- **لینک:** https://www.youtube.com/watch?v=-QFHIoCo-Ko
- **مدت:** حدود ۹۶ دقیقه (ورکشاپ زنده، با Q&A)
- **ایده‌ی اصلی:** AI یک پارادایم کاملاً جدید نیست. اصول پایه‌ی مهندسی نرم‌افزار (کتاب‌های قدیمی مثل *The Pragmatic Programmer*، *Philosophy of Software Design*، *Refactoring*) همان‌طور که برای تیم انسانی جواب می‌دهد، برای AI هم جواب می‌دهد.

> این نوت از روی متن پیاده‌شده‌ی صدای ویدیو (Whisper) نوشته شده. عددها و اسم‌ها ممکنه جاهایی کمی خطا داشته باشن. زمان‌ها داخل `[ ]` برای پیدا کردن بخش مربوطه در ویدیوئه.

## ۱. دو محدودیت عجیب LLMها `[03:00]`

### ۱.۱ Smart Zone و Dumb Zone
- مفهومی از Dex Hawley (شرکت Human Layer).
- اول هر گفتگو (context تقریباً خالی) LLM بهترین کارش رو می‌کنه، چون «رابطه‌های attention» کم‌ترین فشار رو دارن.
- با اضافه شدن هر token، تعداد رابطه‌های attention **درجه دوم (quadratic)** رشد می‌کنه. مثل اضافه کردن یک تیم به لیگ فوتبال که تعداد بازی‌ها رو خیلی زیاد می‌کنه.
- حدود **۴۰٪** context یا حدود **۱۰۰K token** (فرقی نداره context window ۲۰۰K باشه یا ۱ میلیون) مدل شروع می‌کنه به گیج شدن و تصمیم‌های بد گرفتن.
- پنجره‌ی ۱ میلیونی عملاً «Dumb Zone» بیشتری بهت می‌ده. برای **retrieval** (پیدا کردن چیز در متن‌های بزرگ) خوبه، برای **کدنویسی** نه.
- نتیجه: **تسک‌ها رو طوری سایز کن که داخل Smart Zone جا بشن.** (همون توصیه‌ی قدیمی «بیشتر از توانت گاز نزن».)

### ۱.۲ مدل Memento (فراموشی)
- LLM مثل شخصیت فیلم Memento هر بار به حالت پایه برمی‌گرده.
- هر session چهار مرحله داره: **System prompt** (همیشه هست، باید کوچک باشه؛ مثلاً ۲۵۰K token داخلش یعنی از اول وارد Dumb Zone شدی) ← **Explore** ← **Implement** ← **Test/Feedback loops**.
- **Clear** یعنی برگشت به system prompt. **Compact** یعنی فشرده‌سازی تاریخچه‌ی گفتگو.
- Matt **compact رو دوست نداره** و clear رو ترجیح می‌ده، چون state همیشه یکسان و قابل پیش‌بینیه. اگه کارت رو طوری بچینی که با clear هم جور دربیاد، در موقعیت عالی‌ای هستی.
- **همیشه تعداد دقیق token های مصرفی رو ببین** (status line). اگه نمی‌دونی چقدر به Dumb Zone نزدیکی، کور کار می‌کنی.

### ۱.۳ تسک‌های بزرگ رو چطور بشکنیم؟
- روش معمول: **multi-phase plan** (فاز ۱، فاز ۲، ...). Matt تا دسامبر سال قبل همین رو استفاده می‌کرد.
- یک برنامه‌نویس می‌بینه که این یه **loop**ـه: «فاز N» ← اینجاست که **Ralph Wiggum** میاد: یه PRD می‌نویسی که مقصد رو توصیف کنه و به AI می‌گی هر بار یه تغییر کوچک که ما رو نزدیک‌تر کنه انجام بده.
- Ralph جواب می‌ده، ولی Matt ساختار بیشتری می‌خواد (بخش‌های بعد).

## ۲. مرحله‌ی ۱: Grilling (هم‌راستا شدن با AI) `[11:00]`

### مشکل: Specs-to-Code
- ایده‌ی «بنویس spec، بده AI کد بزنه، اگه اشتباه بود spec رو عوض کن و به کد نگاه نکن» در واقع **vibe coding** با اسم دیگه‌ست.
- Matt امتحان کرده و **جواب نمی‌ده**. چون باید کد رو بشناسی و شکلش بدی: «کد میدان نبرد توئه».

### Grill Me skill
- یک skill خیلی کوتاه. خلاصه‌ی دستورش: *«درباره‌ی هر جنبه‌ی این plan بی‌امان از من سؤال بپرس تا به درک مشترک برسیم. هر شاخه‌ی design tree رو دنبال کن، وابستگی‌ها رو یکی‌یکی حل کن، برای هر سؤال جواب پیشنهادی خودت رو بده، سؤال‌ها رو یکی‌یکی بپرس.»*
- مشکلی که حل می‌کنه: AI (مخصوصاً در plan mode) **زیادی مشتاقه که زود plan بده**. ولی چیزی که لازمه «plan» نیست، **درک مشترک (shared design concept)** هست. (اصطلاح از Fred Brooks در *The Design of Design*.)
- نحوه‌ی شروع هر کار: context رو clear می‌کنی، skill رو صدا می‌زنی (`/grill-me`) و brief رو بهش می‌دی. context فقط skill + توضیح کاره.
- مثال دمو: پیام Slack از یک کلاینت (Sarah Chen) که می‌خواد برای پلتفرم دوره‌ی آنلاین (Cadence) gamification اضافه بشه تا retention بره بالا.
- سؤال‌هایی که AI می‌پرسه و خودت به‌تنهایی بهشون فکر نمی‌کردی، مثلاً: «امتیازها retroactive باشن؟ یعنی برای رکوردهای قدیمی backfill کنیم؟»، «کدوم actionها امتیاز می‌گیرن؟»، «streak جدا حساب بشه؟»، «UI گیمیفیکیشن کجا باشه؟»
- معمولاً **توصیه‌ی خود AI خوبه** و فقط تأییدش می‌کنی.
- یک session می‌تونه ۴۰ تا ۱۰۰ سؤال و حتی یک ساعت طول بکشه. خروجیش یک تاریخچه‌ی گفتگوئه که **دارایی (asset)** حساب می‌شه.
- می‌شه **ترنسکریپت جلسه با متخصص حوزه** رو هم بهش داد تا فرض‌های ناگفته رو بیرون بکشه.
- اگه خیلی خسته‌کننده شد، خود skill رو **tune** کن (مثلاً stop point بذار).
- Matt معمولاً به AI **صحبت می‌کنه (dictation)** به جای تایپ.
- از UI ابزار `AskUserQuestion` در Claude Code خوشش نمیاد («از یه جاهایی خرابه»).

### آدم‌ها در چرخه (Human-in-the-loop) در برابر AFK
- دو نوع تسک: **Human-in-the-loop** (باید آدم باشه) و **AFK** (آدم می‌تونه از کیبورد دور باشه).
- **Planning/alignment حتماً human-in-the-loop** است. پیاده‌سازی می‌تونه AFK بشه.
- در تیم: جلسه‌ی grill می‌تونه مثل **pair/mob programming با AI** باشه. سؤال‌های دامنه با domain expert، سؤال‌های پیاده‌سازی با هم‌تیمی.

## ۳. مرحله‌ی ۲: PRD = سند «مقصد» `[28:40]`

نیاز به دو سند داریم:
1. **مقصد (Destination)** ← PRD
2. **مسیر (Journey)** ← Kanban board (بخش بعد)

### Write-a-PRD skill
- بعد از grill، می‌گی «write a PRD». skill: توضیح مشکل ← explore repo ← (مصاحبه) ← پر کردن template.
- ساختار PRD: **Problem Statement**، **Solution**، **User Stories** (مثال: ۱۸ تا)، **Implementation Decisions**، **Testing Decisions**، و **Out of Scope** (مهم برای تعریف «done» و ثبت تصمیم‌های «نه»).
- نکته‌ی کلیدی: **کد رو در نظر داشته باش**. AI لیست **ماژول‌هایی که قراره تغییر کنن** رو پیشنهاد می‌ده و تو تأیید می‌کنی (این Specs-to-Code نیست).
- Matt PRD ها رو داخل **GitHub Issues** می‌ذاره (۷۴۴ issue بسته در repo خودش). در دمو به‌صورت فایل markdown محلی.
- **PRD رو نمی‌خونه!** دلیل: بعد از grill، تو و AI یک درک مشترک دارید. خوندن PRD فقط تست توانایی خلاصه‌سازی LLMه که در آن خوبه.

## ۴. مرحله‌ی ۳: Kanban Board به جای Multi-phase Plan `[39:30]`

- PRD رو به **تیکت‌های مستقل با رابطه‌ی blocking** بشکن (فایل‌های markdown محلی یا GitHub issue).
- هر تیکت نوعش مشخصه: **AFK** یا **Human-in-the-loop**.
- مزیت نسبت به plan ترتیبی: به‌جای یک خط، یک **گراف جهت‌دار بدون دور (DAG)** داری. تیکت‌های بدون وابستگی رو **چند agent هم‌زمان** می‌تونن بردارن. plan ترتیبی فقط توسط یک agent قابل اجراست.
- در QA مشکل پیدا کردی؟ **تیکت جدید به board اضافه کن**، حتی وسط پیاده‌سازی.

### Tracer Bullets / Vertical Slices
- (ایده از *The Pragmatic Programmer*.) tracer bullet گلوله‌ایه که فسفر داره و مسیرش در آسمان دیده می‌شه، یعنی **فیدبک فوری**.
- AI عاشق **کدنویسی افقی (horizontal)** است: اول کل دیتابیس، بعد کل API، بعد کل فرانت‌اند. مشکل: تا فاز ۳ هیچ فیدبکی نداری و سیستم یکپارچه برای تست نیست.
- درست: **برش عمودی (vertical slice)**: یک تکه‌ی نازک که همه‌ی لایه‌ها رو قطع می‌کنه (تغییر schema + سرویس جدید + یک نمایش حداقلی در front-end).
- مثال دمو: AI اول پیشنهاد «فقط gamification service» داد (افقی). Matt اصلاحش کرد به «ثبت امتیاز تکمیل درس + نمایش در داشبورد» (عمودی).
- این skill اسمش PRD-to-issues است و قواعد vertical slice داخلشه.
- **این مرحله رو خودت review کن.** ارزونه و مشکل‌ها سریع دیده می‌شن.
- «روز شیفت / شب شیفت»: انسان در شیفت روز planning می‌کنه و شب AI به‌صورت AFK کار می‌کنه.

## ۵. مرحله‌ی ۴: پیاده‌سازی AFK (Ralph Loop) `[53:50]`

### ساختار
- یک اسکریپت bash (`once.sh`) که:
  1. همه‌ی issueهای markdown رو داخل یک متغیر می‌ریزه،
  2. ۵ commit آخر رو می‌گیره (برای اینکه agent بفهمه چی انجام شده)،
  3. prompt رو می‌خونه،
  4. Claude Code رو با permission mode مناسب اجرا می‌کنه.
- نسخه‌ی AFK (loop واقعی) داخل **Docker sandbox** اجرا می‌شه.
- اول **یک‌بار** (human-in-the-loop) اجراش کن و ببین agent چه می‌کنه، بعد prompt رو tune کن، بعد loop کن.

### Prompt ی implementer
- فقط روی issueهای AFK کار کن.
- اگه چیزی نمونده خروجی «no more tasks» بده.
- اولویت: **bug های critical ← زیرساخت توسعه ← tracer bullet ها ← polish/quick win/refactor**.
- repo رو explore کن، با **TDD** پیاده کن، و **feedback loop** ها رو اجرا کن.

### TDD (Red-Green-Refactor) `[66:40]`
- برای گرفتن بهترین نتیجه از agent «ضروری» است.
- AI اگه تست رو بعد از پیاده‌سازی بنویسه، تقلب می‌کنه (تست‌هایی که همیشه پاس می‌شن). با TDD اول تست شکست‌خورده می‌نویسه، بعد کد رو.
- داخل repo یک skill هست که red-green-refactor رو به AI یاد می‌ده.

### Feedback Loops
- بدون **feedback loop** (تست، type check، lint) AI کور کد می‌زنه.
- **کیفیت feedback loop = سقف کیفیت خروجی AI.** اگه خروجی بد می‌گیری، اول کیفیت feedback loop ها رو بالا ببر.
- در دمو: `npm run test` و `npm run typecheck` اجرا شدن، یک type error پیدا و رفع شد و ۲۸۴ تست پاس شد.

### Review خودکار
- بعد از پیاده‌سازی، **یک review خودکار** با AI بذار (توکن ارزونه و AI در review خوبه).
- **حتماً context رو clear کن قبل از review.** اگه review داخل همون session باشه، reviewer در Dumb Zone کار می‌کنه و از implementer هم کودن‌تره.

## ۶. QA دستی، نقطه‌ی حیاتی `[69:00]`

- بعد از loop، خودت نرم‌افزار رو دستی تست می‌کنی (در دمو: login به‌عنوان دانشجو، تکمیل درس، که به‌خاطر نبودن table در migration خطا داد).
- **QA جاییه که سلیقه‌ی خودت رو روی codebase اعمال می‌کنی.**
- تیم‌هایی که همه‌چیز (ایده، research، prototype، QA) رو اتوماتیک می‌کنن، اپ‌های «بی‌سلیقه» و slop تحویل می‌دن.
- خروجی QA = **تیکت‌های جدید برای Kanban board**.
- ترتیب review کد: اول **تست‌ها** (درست چیز معقولی رو تست می‌کنن؟) بعد خود کد.

## ۷. Codebase بد، Agent بد می‌سازه `[73:40]`

### Deep Modules در برابر Shallow Modules
(از کتاب John Ousterhout، *A Philosophy of Software Design*)

| | Shallow Modules | Deep Modules |
|---|---|---|
| شکل | کلی فایل ریز با export های زیاد | ماژول با **interface کوچک و ساده** و **کارکرد زیاد داخلش** |
| برای AI | ناوبری سخت، باید کل گراف وابستگی رو دنبال کنه | به‌راحتی می‌فهمه |
| تست | مرز تست نامشخصه؛ mock کردن همه‌چیز | **یک مرز تست بزرگ** دور ماژول، کافیه |

- AI بدون نظارت **shallow module** تولید می‌کنه و هر تابع ریز رو جدا تست می‌کنه.
- داخل PRD مشخص کن کدوم **ماژول‌های deep** ساخته/تغییر می‌کنن و نقشه‌ی ماژول‌ها رو همیشه در ذهنت داشته باش.

### حفظ شناخت از codebase
- خیلی‌ها می‌گن «بیشتر از قبل کار می‌کنم و codebase رو کمتر می‌شناسم». خطرناکه چون شکل کد به AI واگذار می‌شه.
- راه‌حل: **interface ماژول‌ها رو خودت طراحی کن، پیاده‌سازی رو واگذار کن.** ماژول‌ها «جعبه‌ی خاکستری» می‌شن: شکل و رفتارشون رو می‌دونی ولی لازم نیست همه‌ی داخلش رو review کنی.

### Skill ی «improve codebase architecture»
- codebase رو اسکن می‌کنه و **کاندیداهای deepening** پیدا می‌کنه (خوشه‌ی ماژول‌های مرتبط که می‌شه یک‌جا تست کرد).
- مثال: سرویس quiz scoring که صفر تست داشت.
- Matt با همین skill برای ادیتور ویدیوی داخل مرورگرش یک ماژول بزرگ ساخت که کل جریان front-end تا back-end رو تست‌پذیر کرد، و می‌گه «تفاوتش شب و روز بود».
- **اگه فقط یک چیز از ورکشاپ رو امتحان می‌کنی، این skill رو روی repo خودت اجرا کن.**

## ۸. Push در برابر Pull (استانداردهای کدنویسی) `[88:00]`

- **Push:** دستورالعمل همیشه به agent فرستاده می‌شه (مثلاً `CLAUDE.md`).
- **Pull:** agent در صورت نیاز خودش اطلاعات رو می‌کشه (مثلاً **skills** با یک description کوتاه).
- توصیه:
  - **Implementer** ← استانداردها به‌صورت **pull** (اگه سؤال داشت بپرسه).
  - **Reviewer** ← استانداردها **push** بشن (کد + استاندارد هر دو در context باشن).

## ۹. اجرای موازی با Sandcastle `[89:50]`

- ابزار شخصی Matt (کتابخانه‌ی TypeScript) برای اجرای loop های AFK.
- جریان کار:
  1. **Planner:** backlog رو می‌خونه و تیکت‌های بدون وابستگی رو برای کار هم‌زمان انتخاب می‌کنه.
  2. برای هر issue یک **git worktree + Docker sandbox** ساخته می‌شه.
  3. **Implementer** داخل sandbox روی branch خودش کار می‌کنه.
  4. اگه commit ای ساخته شد، **Reviewer** اون رو بررسی می‌کنه.
  5. **Merger agent** branch ها رو merge و مشکلات type/test رو رفع می‌کنه.
- مدل‌ها: **Sonnet برای پیاده‌سازی، Opus برای review** (review به هوش بیشتر نیاز داره).

## ۱۰. جمع‌بندی جریان کار

```
ایده
  ↓  Grill Me (human-in-the-loop، رسیدن به درک مشترک)
[در صورت نیاز: Research / Prototype]
  ↓
PRD  (سند مقصد، خودمون نمی‌خونیمش)
  ↓  PRD → Issues (vertical slices / tracer bullets)
Kanban Board  (DAG با رابطه‌ی blocking، review انسانی)
  ↓  ─── انسان از loop خارج می‌شه (شیفت شب) ───
Implement (Ralph loop، TDD، feedback loops، sandbox، موازی)
  ↓  Automated Review (با context تمیز)
QA دستی + code review  ──→ تیکت‌های جدید به Kanban
  ↓
Review تیمی و merge
```

- در تمام مراحل **شکل codebase** رو در نظر داشته باش (Deep Modules).
- در مرحله‌ی ایده تا PRD با تیم هم‌کاری کن (RFC، prototype، research) و بین فازها رفت‌وبرگشت طبیعیه.

## ۱۱. نکته‌های پراکنده از Q&A

- **Spec Kit / OpenSpec / Task Master:** هنوز برنده‌ی مشخصی نیست و همه‌چیز تغییر می‌کنه. **تا جایی که می‌شه خودت مالک stack برنامه‌ریزیت باش** (inversion of control) تا بتونی عیب‌یابیش کنی.
- **PRD رو نگه ندار:** بعد از پیاده‌سازی به‌مرور با کد واقعی فاصله می‌گیره و **doc rot** می‌شه و agent های آینده رو گمراه می‌کنه. Matt issue رو **close** می‌کنه (قابل fetch ولی با نشانه‌ی «تمام‌شده»).
- **PRD رو تا حد کمال optimize نکن:** مسیر فقط یک hint از مقصده. وقتت رو در **grill اولیه و QA** بذار.
- **front-end و AI:** AI چشم نداره. ابزارهایی مثل Playwright MCP هست ولی هنوز خوب نیست. بهتره بگی «۳ prototype در یک route موقت بساز» و بینشون انتخاب کنی، بعد اون رو به grill برگردونی.
- **بیشتر code review:** اگه همه‌ی کدنویسی رو به agent بدی، review و QA بیشتری باید بکنی. Matt جواب قطعی نداره و می‌گه «باید برای review بیشتر آماده بود».
- **پرامپت «sacrifice grammar for the sake of concision»** (برای plan های مختصر): دیگه استفاده نمی‌کنه چون plan ها رو نمی‌خونه، فقط grill می‌کنه.
- **PM ها / نقش‌ها:** نظر قطعی نداره.
- **مدل Claude Code:** «بدترین ابزار، به‌جز بقیه‌ی ابزارها».
